# Deploying ShopEx on Render + Neon

This guide deploys ShopEx from the GitHub repository
[`tigamer20/shopEx`](https://github.com/tigamer20/shopEx):

- the **API** and the **web app** on [Render](https://render.com), from the Blueprint in
  [`render.yaml`](../render.yaml);
- the **PostgreSQL database** on [Neon](https://neon.com), a serverless Postgres host with a
  permanent free plan.

Everything runs in the same AWS region, **US East (Ohio)**: Render `ohio` for the API, Neon
`aws-us-east-2` for the database. Following the guide end to end takes about 30 minutes, most of it
waiting for the first builds.

> Free-tier facts below were checked on render.com/docs/free and neon.com/pricing in November
> 2026. Both providers change their offers from time to time: confirm them on
> <https://render.com/pricing> and <https://neon.com/pricing> before you rely on them.

---

## What gets created

| Resource | Where | Source | What it does |
|---|---|---|---|
| Neon project `shopex` | Neon, **Free** plan, AWS US East 2 (Ohio) | n/a | PostgreSQL: users, grocery lists, stores, catalog and prices |
| `shopex-api` | Render web service, Python runtime, **free** plan, region `ohio` | `backend/` | FastAPI app: `uvicorn app.main:app`, health check `/api/v1/health` |
| `shopex-web` | Render static site (global CDN, no region) | `client/` | Expo web build (`npx expo export -p web` → `dist/`) |

How they connect:

- `shopex-api` reads the Neon connection string from `DATABASE_URL`. The Blueprint declares it
  with `sync: false`, so Render **asks you for the value** when the Blueprint is created and stores
  it as a secret. It is never written in the repository.
- The API rewrites `postgres://` / `postgresql://` to the psycopg 3 driver by itself and keeps the
  query string (`sslmode=require`, `channel_binding=require`) intact. Paste the string exactly as
  Neon shows it.
- Neon suspends an idle database after 5 minutes. The API tests each pooled connection before
  using it (`pool_pre_ping`) and replaces connections older than 5 minutes (`pool_recycle`), so a
  sleeping database only costs a short delay on the next request, never an error.
- `JWT_SECRET` and `ADMIN_TOKEN` are **generated by Render** (random values) the first time the
  Blueprint is applied. They are never stored in the repository.
- `shopex-web` calls the API at the URL baked into the bundle at build time
  (`EXPO_PUBLIC_API_URL`), and the API only accepts browser calls from the origins in
  `CORS_ORIGINS`.
- Both Render services use `autoDeployTrigger: checksPass`: a push to `main` is deployed only after
  the GitHub Actions CI checks of that commit have passed.
- Regions cannot be changed after creation, neither on Render nor on Neon. Keep the API and the
  database in Ohio: every API request makes several database round trips.

## 1. Create the database on Neon

1. Go to <https://neon.com> and click **Sign up**. Signing up with GitHub is the quickest. The Free
   plan is permanent (not a trial) and **needs no credit card**.
2. Create a project:
   - **Project name**: `shopex`.
   - **Cloud provider / region**: **AWS**, **US East 2 (Ohio)** (`aws-us-east-2`). This cannot be
     changed later.
   - **Postgres version**: keep the default.
   - If Neon asks what you want to build, choose **Just Postgres**: ShopEx only needs the database
     (it has its own accounts and does not use Neon Auth, storage or functions).
   - Click **Create project**. Neon creates a `main` branch, a database (`neondb` by default) and a
     role that owns it.
3. On the project dashboard, click **Connect**. In the dialog:
   - keep the `main` branch, the default database and its role;
   - make sure **Connection pooling** is **on**: the host name must contain **`-pooler`**;
   - copy the connection string. It looks like
     `postgresql://<role>:<password>@ep-<name>-pooler.us-east-2.aws.neon.tech/neondb?sslmode=require&channel_binding=require`.
4. Keep the string somewhere private for the next step (a password manager, or just the clipboard).
   **It contains the database password.** Never put it in the code, in `.env.example`, in a commit,
   in an issue, or in a chat message. If it leaks, reset the role's password in Neon
   (**Roles > Reset password**) and update `DATABASE_URL` on Render.

Why the pooled string: Neon's pooler (PgBouncer) lets many short-lived connections share a few
database connections, which suits a web API. ShopEx creates its tables with plain SQL at startup and
needs no session features, so it works through the pooler without changes.

## 2. Deploy the Blueprint on Render

1. Make sure CI is green on `main` (GitHub → **Actions** → **CI**).
2. Sign up at <https://render.com> (with GitHub is simplest, it grants repository access).
3. In the Render Dashboard, click **New > Blueprint**.
4. Connect your GitHub account if asked, then click **Connect** next to `tigamer20/shopEx`.
5. Name the Blueprint (for example `shopex`) and select the `main` branch. Leave **Blueprint Path**
   empty: Render reads `render.yaml` at the repository root.
6. Review the resources: **two services** (`shopex-api`, `shopex-web`) and no database. Render
   shows an input for **`DATABASE_URL`** on `shopex-api`: paste the Neon pooled connection string
   from step 1.
7. Click **Deploy Blueprint**.

Render prompts for `sync: false` values **only when the Blueprint is first created**. If you are
switching an existing ShopEx Blueprint (for example one that used a Render database), set the value
by hand instead: `shopex-api` → **Environment** → `DATABASE_URL` → paste the Neon string → **Save,
rebuild, and deploy**. Then delete the old Render database from the dashboard once you no longer
need its data.

The first API build takes a few minutes (`pip install -r requirements.txt`); the web build runs
`npm ci` and the Expo export.

## 3. Check the first deploy

1. **API**: open `https://<api-host>/api/v1/health`. Expect `{"status":"ok","version":"..."}`.
   On its first start the API creates its tables in Neon and seeds the catalog (see the service's
   **Logs** tab if the check fails). In Neon, **Tables** now lists `users`, `stores`, `prices`, ...
2. **Web**: open `https://<web-host>/`. You should see the onboarding tutorial, then the login
   screen.
3. Create an account and run a search to confirm the web app reaches the API.

## 4. Set the real URLs (CORS and API URL)

Look at the URL Render shows at the top of each service page. If they are exactly
`https://shopex-api.onrender.com` and `https://shopex-web.onrender.com`, skip this step: the
Blueprint already uses them.

Otherwise (Render added a suffix such as `shopex-api-a1b2.onrender.com` because the name was
taken), edit **`render.yaml`** (not the dashboard: on every Blueprint sync, values defined in the
file overwrite values changed in the dashboard):

| Where in `render.yaml` | Set it to |
|---|---|
| `shopex-api` → `CORS_ORIGINS` | the web URL, e.g. `https://shopex-web-a1b2.onrender.com` (no trailing slash; comma-separate several origins) |
| `shopex-web` → `EXPO_PUBLIC_API_URL` | the API URL, e.g. `https://shopex-api-a1b2.onrender.com` |
| `shopex-web` → `Content-Security-Policy` header → `connect-src` | the same API URL |

Also update `EXPO_PUBLIC_API_URL` in `client/eas.json` (preview and production profiles) so the
mobile apps use the same API.

Commit and push to `main`. Once CI passes, Render syncs the Blueprint and redeploys. Because
`EXPO_PUBLIC_*` values are compiled into the web bundle, the static site must be **rebuilt** to pick
up a new API URL; the push does this. To force it manually, use **Manual Deploy > Clear build cache
& deploy** on `shopex-web`. `DATABASE_URL` is not touched by syncs (`sync: false`).

> Why not reference the API host automatically? A Blueprint `fromService` host reference resolves
> to the service's private-network hostname, which browsers cannot reach, and static sites cannot
> use Render's private network. The public URL therefore has to be written down once.

## 5. Daily refresh with GitHub Actions

Free Render services sleep when idle, so ShopEx refreshes its data from a scheduled GitHub Actions
workflow ([`.github/workflows/daily-refresh.yml`](../.github/workflows/daily-refresh.yml)) instead
of a loop inside the API. It runs every day at 09:00 UTC: it first wakes the API with a few health
check retries, then calls `POST /api/v1/admin/refresh` with the admin token.

1. In Render, open `shopex-api` → **Environment** and reveal `ADMIN_TOKEN`. Copy it.
2. In GitHub, open the repository → **Settings > Secrets and variables > Actions** →
   **New repository secret**, and add:

   | Secret | Value |
   |---|---|
   | `SHOPEX_API_URL` | the API URL, e.g. `https://shopex-api.onrender.com` (no trailing slash needed) |
   | `SHOPEX_ADMIN_TOKEN` | the `ADMIN_TOKEN` value copied from Render |

3. Run it once by hand: **Actions > Daily refresh > Run workflow**. The log ends with a JSON summary
   (`areas_refreshed`, `stores_refreshed`, `prices_updated`, timestamps). The token is never printed.

Notes:

- Treat `ADMIN_TOKEN` like a password. To rotate it, generate a new value
  (`python -c "import secrets; print(secrets.token_urlsafe(48))"`), set it on `shopex-api` in the
  dashboard, then update the GitHub secret. `generateValue` only creates a value when none exists,
  so a Blueprint sync will not overwrite yours.
- GitHub may run scheduled workflows a few minutes late, and it **disables schedules in public
  repositories after 60 days without repository activity**. Re-enable the workflow from the
  Actions tab if that happens.
- To refresh from your own machine instead, run `python -m app.jobs.refresh` from `backend/` with
  `DATABASE_URL` set **in your shell** (not in a committed file) to the Neon connection string.

## 6. Custom domain (optional)

1. On each Render service, open **Settings > Custom Domains** and add your domains, for example
   `app.example.com` on `shopex-web` and `api.example.com` on `shopex-api`.
2. Create the DNS records Render shows (typically a `CNAME` to the service's `onrender.com` host;
   remove `AAAA` records). Render verifies the domain and issues and renews the TLS certificate
   automatically.
3. Update the same places as in step 4 with the new origins: `CORS_ORIGINS`,
   `EXPO_PUBLIC_API_URL`, CSP `connect-src`, `client/eas.json`, and the `SHOPEX_API_URL` GitHub
   secret. Push to `main`.

The `onrender.com` addresses keep working unless you disable them. Neon needs no change.

## 7. Free-tier caveats

| Topic | What to expect | What ShopEx does about it |
|---|---|---|
| **Render: spin-down** | A free web service sleeps after **15 minutes** without inbound traffic. The next request wakes it, which takes **about a minute**. | The app shows loading states; the daily refresh wakes the API before calling it. The first search of the day is slow. |
| **Render: instance hours** | **750 free instance hours** per workspace per calendar month; unused hours do not roll over. If they run out, free services are suspended until the next month. | One API that sleeps when idle fits easily. Avoid other free services in the same workspace. |
| **Render: restarts** | Free services can be restarted at any time and have no persistent disk; local files are lost. | All state lives in Neon; in-memory login rate-limit counters reset on restart. |
| **Neon: scale to zero** | The database compute **suspends after 5 minutes** of inactivity (cannot be disabled on Free) and resumes on the next query, usually within a second. | `pool_pre_ping` and `pool_recycle=300` replace dropped connections transparently. |
| **Neon: storage** | **1 GB** per project (20 GB across projects). Beyond it, **writes are blocked**; data is not deleted. | The data set is small (catalog + prices for discovered areas). Watch **Monitoring** if many areas get searched. |
| **Neon: compute** | **100 CU-hours** per project per month, autoscaling up to 2 CU. If they run out, compute is suspended until the next billing period. | Scale to zero means hours are only used while the API talks to the database. |
| **Neon: network transfer** | **5 GB** egress per project per month; same suspension rule. | API responses are paginated and small. |
| **Neon: recovery** | Free includes a 6-hour history window and 1 manual snapshot; no scheduled snapshots. | Take a manual snapshot before risky changes. Accounts and lists are the only data that cannot be regenerated. |
| **Static site** | Free; counts against the workspace's monthly bandwidth and build minutes. | Hashed bundles are cached for a year (`Cache-Control: immutable`). |
| **Third-party servers** | Overpass, OSRM demo server and OSM tiles are free community services with fair-use policies. | Stores are cached per area for 24 h; for real traffic set `OSRM_URL` and `EXPO_PUBLIC_TILE_URL` to services you control or pay for. |

Unlike Render's free Postgres, a Neon Free project **does not expire**: accounts and lists persist.

## 8. Costs: free vs paid upgrade path

Check <https://render.com/pricing> and <https://neon.com/pricing> for current prices.

| Stage | API (`shopex-api`) | Database (Neon) | Web (`shopex-web`) | Approx. total |
|---|---|---|---|---|
| **Demo / hobby** (this guide) | Render Free (sleeps when idle) | Neon Free | Free | **$0** |
| **Small production** | Render Starter, 0.5 CPU / 512 MB, always on: ~$7/month | Neon Launch: usage-based (compute hours + storage), a few dollars for a small app | Free | **~$10–20/month** |
| **Growing** | Render Standard, 1 CPU / 2 GB: ~$25/month | Neon Launch or Scale: usage-based | Free | **~$35–60/month** |

To upgrade the API, change its instance type (**Settings > Instance Type**) or set `plan:` in
`render.yaml` to a paid instance type from the [Blueprint spec](https://render.com/docs/blueprint-spec)
and push. To upgrade the database, change the plan in the Neon Console (**Billing**): the project
and its data stay in place and `DATABASE_URL` does not change.

When the API runs on a paid, always-on instance you may set `DAILY_REFRESH_IN_PROCESS=true` and
remove the GitHub schedule, but keeping the external job is harmless and works on every plan.

## 9. Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| API build fails while installing a package | Python version mismatch | `PYTHON_VERSION` in `render.yaml` must be a fully qualified, released version (e.g. `3.14.8`). |
| API deploy fails, log says `JWT_SECRET must be set` | `ENV=production` without a secret of 32+ characters | Make sure the `JWT_SECRET` variable exists on `shopex-api` (the Blueprint generates it); set one manually if it was deleted. |
| API log shows `sqlite` or `unable to open database file` | `DATABASE_URL` is empty on Render | Set it in `shopex-api` → **Environment** (step 2). `sync: false` values are only prompted on the first Blueprint creation. |
| `SSL connection is required`, `SSL SYSCALL error` or `channel binding` errors | The query string was cut when pasting | Paste the full Neon string, including `?sslmode=require&channel_binding=require`. Do not remove `sslmode`: Neon only accepts TLS. |
| `password authentication failed` | Wrong or reset role password | Copy a fresh string from Neon **Connect** (or reset the password there) and update `DATABASE_URL`. |
| `could not translate host name` / `endpoint ... not found` | Typo in the host, or the project/branch was deleted | Copy the string again from **Connect**; check the project still exists. |
| First request after a quiet period takes ~1 minute | Render cold start (plus a sub-second Neon resume) | Expected on the free plans (section 7). Errors at that moment are not expected: check the logs. |
| `server closed the connection unexpectedly` in logs | A connection dropped while Neon was suspended | Handled by `pool_pre_ping`; if it repeats, make sure you deployed the current `backend/app/db.py`. |
| `too many connections` | Direct (non-pooled) string in use | Use the **pooled** string (host contains `-pooler`). |
| Writes fail with a storage or quota message | Neon Free storage (1 GB) or compute/egress allowance used up | Check the Neon **Monitoring** and **Billing** pages; upgrade or wait for the next billing period. |
| Web app loads but every call fails, console shows a **CORS** error | `CORS_ORIGINS` does not exactly match the web origin | Use the exact origin, `https://` and no trailing slash; push the `render.yaml` change. A CORS error also appears when the API is down or still waking up: open `/api/v1/health` first. |
| Web app calls `localhost:8000` or an old API | `EXPO_PUBLIC_API_URL` was wrong at build time | Fix it in `render.yaml`, push, or **Clear build cache & deploy** `shopex-web`. |
| Console shows **Content Security Policy** violations | API or tile host not in the CSP | Add the host to `connect-src` (API) or `img-src` (tiles) in the `shopex-web` headers. |
| Web build succeeds but the deploy says the publish directory is missing | `staticPublishPath` resolved from the wrong folder | It is relative to `rootDir` (`client/`), so `dist` means `client/dist`; check the build log for the folder `expo export` wrote. |
| Refreshing a deep link (e.g. `/results`) returns 404 | SPA rewrite missing | Keep the `/*` → `/index.html` rewrite in `render.yaml`. |
| Map stays grey | Tiles blocked or rate-limited | Check the browser console; OSM tiles need a `Referer` (the `Referrer-Policy` header keeps it). |
| Daily refresh fails with **404** | `ADMIN_TOKEN` is not set on the API (endpoint disabled) | Set `ADMIN_TOKEN` on `shopex-api`. |
| Daily refresh fails with **403** | GitHub secret differs from the API's `ADMIN_TOKEN` | Copy the value again into `SHOPEX_ADMIN_TOKEN`. |
| Daily refresh times out | Cold start plus slow Overpass responses | Re-run the workflow; check the `shopex-api` logs. |
| Searches return no stores | Overpass unreachable or rate-limited (`DEMO_STORES_FALLBACK` is off in production) | Retry later, or point `OVERPASS_URL` to another Overpass instance. |
| Login answers **429** | Five failed logins in five minutes for that email and IP | Wait five minutes. |

Logs: each Render service has a **Logs** tab and the Blueprint page shows sync history and errors;
Neon shows database activity under **Monitoring**.

## 10. Alternative hosts

ShopEx is a standard FastAPI app plus a static web build, and any PostgreSQL works as the
database, so it runs almost anywhere. Rough comparison (late 2026; prices change often, so check
each provider):

| Option | Fit for ShopEx | Free tier | Paid notes |
|---|---|---|---|
| **Render + Neon** (this guide) | Blueprint deploys the API and web app; Neon hosts Postgres | Web service sleeps when idle; Neon Free is permanent; static sites free | ~$10–20/month for an always-on API + small Neon usage |
| **Fly.io** | Runs the API as a container (add a Dockerfile); global regions | No free allowance for new accounts; pay as you go | Small machines cost a few dollars a month; can keep using Neon |
| **Railway** | Deploys `backend/` and Postgres from the repo with little config | One-time trial credit | Hobby plan with a monthly fee that includes some usage; billed by resource usage |
| **Vercel + Render** | Web app on Vercel's CDN (needs a `vercel.json` for the SPA rewrite and headers); API on Render, database on Neon | Vercel Hobby is free for **non-commercial** use | Vercel Pro is billed per seat; Render and Neon costs as above |
| **Azure App Service** | API on App Service (Linux, Python), web on Azure Static Web Apps, Azure Database for PostgreSQL | App Service F1 (CPU quota, no always-on); Static Web Apps free plan; 12-month free database offer for new accounts | Basic B1 App Service plus a Burstable Postgres server, roughly $25–40/month |
| **AWS** | API on Elastic Beanstalk, ECS Fargate or Lightsail containers; web on S3 + CloudFront or Amplify; RDS PostgreSQL | Credits-based free plan for new accounts | Most flexible and most setup (IAM, networking); small setups typically $20–40/month |

Whatever the host, keep the same rules: secrets in environment variables only, `ENV=production`,
HTTPS (and `sslmode=require` to the database), exact `CORS_ORIGINS`, the security headers from
`render.yaml`, and deploy only after CI passes.
